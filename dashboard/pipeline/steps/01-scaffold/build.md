## 4. The type contract — shape and reasoning

`lib/types.ts`. Read it top to bottom; this section is the argument, not a summary of the
fields.

### 4.1 Every reading is `T | null`, and the census proves it

§3's opening sentence and invariant 1 are the whole design. The nullable unit is the
**reading**, not the object holding it: `tempC`, `fan5Rpm`, `utilPct`, `ufwEnforcing` are
each `T | null` individually.

`lib/types.test-d.ts` asserts the *exact* set of members allowed to be non-nullable, per
type. Adding a field that forgets its `| null` fails by name. The permitted exceptions,
and why each one is not a reading:

| Type | Non-nullable | Why |
|---|---|---|
| `Gpu` | `index` | Identity. §6.2 joins serving data onto the GPU card **by index**; a row whose index did not parse cannot be placed in a panel, so it is an `errors[]` entry rather than a GPU |
| `ServingInstance` | `instance` | Identity, taken from the `/etc/llama-server/<i>.env` filename |
| `CoolingManual` | `ch5Mode`, `ch5Pwm` | See §4.3 — a numeric `pwm5` read is what *makes* the mode manual, so the value exists by construction |
| `CoolingEcAuto` | `ch5Mode` | The discriminant |
| `Storage` | `root`, `home`, `net` | Containers, not readings |
| `TelemetryError` | `source`, `message` | An error that could not say what failed is useless |
| `TelemetrySnapshot` | `ts`, `host`, `cooling`, `storage`, `safety`, `errors` | See §4.2 |

`Host`, `CoolingChannels`, `Filesystem`, `Network`, `Safety` have **no** non-nullable
members at all.

`LoadAverage` is the one reading nullable as a whole rather than per-element
(`readonly [number, number, number] | null`). All three figures come from one line of one
file in a single read; there is no state of the machine where the 5-minute average parses
and the 1-minute one does not, and §6.6 has no rendering for half a load average.

### 4.2 Which containers can be `null`, and the `null` vs `[]` distinction

- `host`, `cooling`, `storage`, `safety` are **never** `null`. §6.5: "A single sensor read
  fails → that figure shows `—` … the rest of the panel renders." A nullable container
  would let one bad sensor blank a whole panel, which is the opposite of what §6.5 asks
  for.
- `gpus` and `serving` **are** nullable, and `null` is not `[]`. `[]` means the
  enumeration ran and found nothing — a state this box was genuinely in for weeks. `null`
  means the enumeration could not be performed at all. §3.1 renders both as "no GPUs
  enumerated", which is fine; the contract keeps the two facts apart and `errors[]` says
  which happened. **This is my extension of invariant 1 to a list, not something §3.1
  spells out** — §3.1 says only that "`nvidia-smi` missing or returning nothing" gets one
  presentation. Called out here so the adversarial phase can reject it if it disagrees;
  rejecting it costs one type change and no behaviour.
- `errors` is never `null`. An empty array is a complete snapshot.
- `ts` is never `null` — the server always knows what time it is.

There is **no** "last successful read" field, despite §3.1 mentioning "the timestamp of
the last successful read". §4 fixes the server as stateless ("Sampling is per-request, not
a background loop", "The server holds no history at all"), so that timestamp is
necessarily derived by the client from its own ring buffer (§6.7). This is a derivation
from the spec, not a gap.

### 4.3 Channel 5 is a discriminated union

§3.3's derivation is encoded, not commented:

```ts
interface CoolingManual      extends CoolingChannels { ch5Mode: 'manual';  ch5Pwm: Pwm  }
interface CoolingEcAuto      extends CoolingChannels { ch5Mode: 'ec-auto'; ch5Pwm: null }
interface CoolingUnavailable extends CoolingChannels { ch5Mode: null;      ch5Pwm: null }
type Cooling = CoolingManual | CoolingEcAuto | CoolingUnavailable;
```

Three consequences, each covered by a test:

1. `ENODATA` gets its **own variant**, so invariant 3 holds structurally — "EC auto" can
   never be filed under "the read failed", because it is not spelled the same way.
2. A manual channel carries a **non-null** `Pwm`. Narrowing on `ch5Mode === 'manual'`
   reaches the number with no null check, which is correct: the successful numeric read is
   what made the mode manual.
3. The impossible states are unrepresentable. `{ ch5Mode: 'ec-auto', ch5Pwm: 255 }`,
   `{ ch5Mode: null, ch5Pwm: 128 }` and `{ ch5Mode: 'manual', ch5Pwm: null }` are all
   compile errors, each with a `@ts-expect-error` test.

Three concrete interfaces rather than `CoolingChannels & (…union…)`: TypeScript's
narrowing of an intersection-over-union is not something I wanted the contract to depend
on. Plain interfaces narrow unambiguously.

Deliberately **absent** from the contract: `pwmN_enable` and `fanN_target`. Invariant 4
and §3.3 say `fanN_input` is the only trustworthy fan telemetry — `pwmN_enable` reads back
`2` even under manual control, `fanN_target` clamps to the HIGH nominal. Neither is in the
type, so neither can be displayed or derived from by accident.

### 4.4 Branded units

Every quantity is a branded number: `Celsius`, `Watts`, `MiB`, `GiB`, `GB`, `MHz`, `Rpm`,
`Percent`, `BytesPerSecond`, `Seconds`, `Pwm`, `Port`, `Tokens`, plus `IsoTimestamp` and
`ThrottleMask` over `string`.

The justification is §6.6 and decision 20: **three different memory units appear in one
snapshot** — VRAM in MiB, host RAM in GiB, disk in GB — and §6.6 gives each a different
format (thousands-separated MiB, 1 dp GiB, 2 dp for swap, 1 dp GB). Branding makes
`memUsedMiB` unable to reach a GiB formatter. That pays off at step 2, which owns the
formatters, and step 9, which owns the meters.

Brands are erased at runtime. `lib/contract.test.ts` proves the constructors are the
identity function and that a branded value serialises as a plain number, so the JSON is
readable by anything — including the Prometheus scraper §1's non-goals contemplate.

The constructors take `number`, never `number | null`, on purpose. A collector holding a
possibly-absent reading has to write `raw === null ? null : celsius(raw)`, which puts the
decision where it can be seen. A constructor that swallowed `null` would hide it.

### 4.5 Closed vocabularies

No bare `string` where the spec fixes values:

| Type | Members | Source |
|---|---|---|
| `Severity` | `normal` `watch` `alarm` | §6.3. No `unknown` member: a `null` reading has no severity, and paused/stale are *modes* shown alongside severity (§6.2), never instead of it |
| `UnitState` | `active` `reloading` `inactive` `failed` `activating` `deactivating` | systemd's own `ActiveState` vocabulary, complete. See gap 4 |
| `LinkState` | `up` `down` `unknown` `dormant` `notpresent` `lowerlayerdown` `testing` | the kernel's `operstate` vocabulary, complete |
| `HealthState` | `ok` `unhealthy` `unreachable` | **provisional** — see gap 2 |
| `Ch5Mode` | `manual` `ec-auto` | §3.3 |

`TelemetryError.source` is a bare `string`, because §4 gives one example (`"coretemp"`)
and no closed list — see gap 5.

### 4.6 One invariant the types cannot express

`safety.pwm5Present === false` ⟺ `cooling.ch5Mode === null`. Both come from the same
probe. Cross-field dependent typing would need a union over the whole snapshot, which is
worse than the problem, so it is documented in `lib/types.ts` on both fields instead:
whoever assembles the snapshot (step 6) derives one from the other rather than reading
twice. Same for `safety.fanServiceActive`, which is `cooling.serviceState === 'active'`
and shares one D-Bus read. §3.6 lists the fan service as one of the four safety checks, so
both places carry it; the note is there to stop them diverging.

## 5. Tests — and proof they are not vacuous

**34 tests across 2 files.** 21 are type-level (`lib/types.test-d.ts`, run through `tsc` by
Vitest's `typecheck` mode), 13 are runtime (`lib/contract.test.ts`).

The type-level tests use a hand-rolled invariant-identity equality:

```ts
type Equals<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Assert<T extends true> = T;
```

Deliberately **not** assignability, and deliberately not `expectTypeOf().toEqualTypeOf()`
for the census: `never` is assignable to everything and `any` is assignable in both
directions, which is exactly what a loosened contract collapses into. An
assignability-based check would go green for the two cases it most needs to catch.

### Three deliberate regressions, each reverted

Every one of these was actually run.

**A. `"strict": false` in `tsconfig.json`** (with `exactOptionalPropertyTypes` removed, so
the config stays valid):

```

   × TypeScript is strict, and stays strict
   × only identities and containers are non-nullable
   × a nullable temperature is not a temperature
   × a nullable RPM has no methods
   × a nullable percentage cannot be compared to a threshold
   × the GPU list is not an array until the null is handled
   × a nullable disk figure cannot go straight into arithmetic
   × a nullable boolean is not a boolean
   × EC auto has no PWM value at all — and that is healthy, not an error
   × a channel with no pwm5 node cannot be under manual control
```

The `@ts-expect-error` mechanism is the load-bearing one: with `strictNullChecks` off, the
error each directive expects stops existing, and an unused directive is itself a compile
error. A test written this way cannot survive the strictness being turned off.

**B. `Host.cpuTempC` loses its `| null`** (one character short of `Celsius | null`):

```

```

### A real finding about Vitest, which changed the tests

**A compile error at module scope in a `*.test-d.ts` file does not fail `pnpm test`.** The
first draft kept the nullability census as module-scope exported type aliases. Under
regression A, `pnpm typecheck` reported seven `TS2344` errors from those aliases while
`pnpm test` printed `Type Errors  no errors` and never counted them. Vitest attributes a
type error to the test whose *body* contains it and drops the rest.

Every assertion was therefore moved **inside** a `test()` callback, with a local type alias
consumed by `expectTypeOf<…>().toBeArray()`. Regression A then produced 12 failures
instead of 11, the extra one being the census. Anyone adding type-level assertions to this
project must do the same or they will be writing tests that only `pnpm typecheck` runs.

Related, and the reason `lib/contract.test.ts` carries a `tsconfig.json` text assertion at
all: with `"strict": false` but `exactOptionalPropertyTypes` still set, the config is
*invalid* (`TS5052`), `tsc` bails before checking anything, and Vitest reports
`Type Errors  no errors` — a green typecheck on a compiler that never ran. The text
assertion fails immediately in that case and is the only thing that does.

### What the runtime tests cover that the type tests cannot

- **`null` survives the wire.** A 31-path census walks a fully-unreadable snapshot through
  `JSON.parse(JSON.stringify(…))` and asserts, per path, that the key is *present* and the
  value is `null`. This is what catches `field?: T` — `JSON.stringify` drops `undefined`
  properties entirely, so an optional field would arrive with the key simply missing, and
  a client reading it would get `undefined`, which templates render as blank. §6.6 forbids
  blank: `null` renders as `—`.
- **Zero survives the wire as zero.** The same 31 paths against an all-zero snapshot, plus
  explicit `toBe(0)` on `fan5Rpm`, `cpuPct` and `rxBytesPerSec`. Invariant 1, at the
  serialisation layer.
- **The fixtures themselves are the test.** That a snapshot in which *every* reading failed
  compiles, and a snapshot in which every reading is zero also compiles, is a compile-time
  proof checked by both commands.
- **`strict` is still on**, `output: 'standalone'` is still set, and nothing imports
  `next/image` (import-shaped regex, not a substring match, so `next.config.mjs` can
  explain the rule in prose without tripping it).

## 7. Gaps in the spec — invariant 7

Recorded, not filled. Numbers 1 and 2 are the ones that will bite a later step.

### Gap 1 — the CPU panel needs a field the data model does not have

§6.2: "**CPU** — package temperature, aggregate utilisation with a trace, **core/thread
count**, load average."

§3.2's Host table has `cpuPct`, `loadAvg`, `cpuTempC`, memory, `uptimeSec`, `kernel`. There
is **no core/thread count field and no source named for one.** `/proc/cpuinfo`,
`nproc`, `os.cpus().length` and `os.availableParallelism()` are all plausible and would
each give a slightly different answer under `--pid host`.

**I did not add the field.** Adding it means choosing a name and a source, which is the
assumption invariant 7 forbids. Step 10 cannot render §6.2's CPU panel as written until
this is resolved. The machine is a 6C/12T W-2135, so the values are known — what is not
known is whether the spec wants them read or treated as static.

### Gap 2 — `/health` has a source but no vocabulary

§3.4 fixes `health` as `GET http://127.0.0.1:PORT/health` and says it answers without the
API key. §6.2 says the SERVING row shows "the `/health` result". §6.5 says a downed
instance shows "the unit state and the reason". **No values are enumerated anywhere.**

I used `HealthState = 'ok' | 'unhealthy' | 'unreachable'` — the minimal honest model of an
HTTP probe: the server answered and said it was ready; the server answered and said it was
not; the connection did not complete. `null` is a fourth and different thing — the probe
was never attempted, for instance because the port could not be read from the env file.

**This vocabulary is mine, and it is provisional.** Step 5 owns the collector and should
confirm or replace it. llama.cpp's `/health` returns 200 `{"status":"ok"}` or 503 while
loading, which fits, but that is knowledge from outside the spec.

### Gap 3 — the wire value for an unavailable channel 5

§3.3 gives `ch5Mode` exactly two values, `manual | ec-auto`. §6.5 requires a third
presentation — "`pwm5` absent | Cooling panel shows the channel as unavailable" — and §3.6
makes it an alarm. **The spec never says what the JSON carries in that case.**

I used `ch5Mode: null`, because `null` is what every other unreadable field in this
contract carries and invariant 1 makes it the obvious spelling. A string sentinel
(`'unavailable'`) would read better in the JSON but would be a value the spec does not
name either. Either way this is a choice, not a reading of the spec.

### Gap 4 — two systemd states have no severity

§6.3's last row: "Any unit | `active` | `activating` | `failed`/`inactive`". systemd's
`ActiveState` has **six** values; `reloading` and `deactivating` are unmapped.

`UnitState` includes all six, because D-Bus can return them and a collector that could not
represent one would have to lie. But step 2, which owns the severity bands, has no rule
for those two. `reloading` is plausibly `watch`; `deactivating` is plausibly `watch` or
`alarm` depending on whether it is a restart or a shutdown. Not decided here.

### Gap 5 — `errors[].source` has no closed vocabulary

§4's example uses `"coretemp"`, which is finer-grained than §3's section headings
(`gpu`/`host`/`cooling`/…). No list is given. Left as `string`, and flagged: step 6 owns
the route and is the right place to fix a vocabulary if the UI is going to key off it. §6.5
says "its `errors` entry is available", which suggests the UI matches an error to a figure —
that matching needs a stable `source`, and there is nothing to match on today.

### Gap 6 — two safety field names are elided

§4's example shows `"safety": { "ufwEnforcing": false, "pwm5Present": true, ... }`. The
other two checks appear only as §3.6 row labels. I named them
`dkmsBuiltForRunningKernel` and `fanServiceActive`. Low risk, but they are my names.

### Minor observations, not gaps

- **The network interface name is not a snapshot field.** §3.5 fixes it as `eno1` and the
  non-goals rule out multi-host, so the UI label is a constant. If a panel is ever meant to
  show it dynamically, the field does not exist.
- **`hostname` appears in §4 but not in §3.2**, and no source is named. `os.hostname()`
  works under `--pid host`. Typed `string | null`.
- **The GPU↔serving join has no explicit link field.** §6.2 says the model is "joined from
  the serving data by instance index", so the join is `gpu.index === serving.instance`.
  That is what the spec says; it is worth noting that nothing in the contract *asserts*
  instance N is pinned to GPU N, so a future `serve-llm.sh` change that broke that pinning
  would silently mislabel a card.

| Left out | Owner |
|---|---|
| `Severity` is defined but nothing computes it; no threshold bands, no formatters, no standing-condition logic | step 2 |
| No collectors at all. `lib/` holds only the contract | steps 3–5 |

| A condition-id vocabulary for §6.4's `STANDING` list (`ufw_enforcing`) | step 2 |

Two things a later step should carry forward rather than rediscover:

1. **Type-level assertions must live inside `test()` callbacks** or `pnpm test` will not
   run them (§5).
2. **The `Cooling`/`Safety` cross-field invariant** in §4.6 is documented, not enforced.
   Step 6 must derive `pwm5Present` and `fanServiceActive` from the cooling reads rather
   than probing twice.
